# v5.10 — MCP Capability Back-Pressure Closed Loop

> Status: **design draft, 2026-06-24**  ·  Owner: Devin Blagbrough  ·  Task #500

## Motivation

The MCP proxy surface has been live since v5.7.0:

- Path A (`/llm-proxy2/mcp/`) and Path B (auto-inject into `/v1/messages`)
- Per-key allow/deny + token-budget enforcement (v5.7.4)
- `/admin/mcp` dashboard (v5.7.5)
- **Capability scout** (v5.7.6) — scans responses for refusal phrasings ("I can't read PDFs…") and writes `mcp_capability_suggestion` rows to `activity_log`

Today these suggestions are **passive**: the operator sees them in the dashboard and decides whether to flip a per-key allow-list bit. The calling service — the actual bot or app whose work was blocked — never hears about the suggestion.

This ship closes the loop so the **caller** can adopt the recommended MCP tool itself, with the proxy as the routing layer.

## Non-goals (this ship)

- **External MCP server discovery**. Suggestions stay scoped to the in-process tool catalog (`read_xlsx_to_markdown`, `markitdown`, `fetch_url`, plus whatever is registered locally). Crawling a public MCP registry is a separate ship.
- **Modifying assistant `content`**. Inserting suggestion text into the model's reply breaks content-integrity and compliance audit (the model didn't say it). Out of scope, do not do it.
- **MCP-native notifications** for callers using Path A directly. Listed in §10 as Ship 5 — separate, later, optional.

## Protocol surface options (and why we chose what we chose)

| Channel | Pros | Cons | Verdict |
|---|---|---|---|
| HTTP response header (`X-Proxy-MCP-Suggestion` or RFC 5988 `Link`) | Standard, dev-visible, ignored cheaply by callers that don't care | Some SDKs hide headers from app code | **Primary channel** |
| `usage.proxy_metadata` body extension field | SDKs surface `usage` to app code | Modifying response body crosses a compliance line — needs careful audit | **Mirror only**; not the primary signal |
| SSE event (`event: proxy_signal`) on streaming `/v1/messages` | Already inject `event: budget` etc. | Only fires when caller streams | **Ship 4 (optional)** |
| MCP-native `notifications/proxy_suggestion` | Protocol-correct for MCP-using callers | Only reaches Path A users | **Ship 5 (optional)** |
| Inserted into assistant `content` | Universal | Breaks content integrity, audit, risks model echoing on next turn | **NEVER** |

## Ship 1 — Header emission (`X-Proxy-MCP-Suggestion`)

**Scope** ~2-3h, primary surface.

### Header format

```
X-Proxy-MCP-Suggestion: {"tool":"read_xlsx_to_markdown","reason":"refusal","confidence":0.78,"adopt_via":"X-Proxy-Accept-MCP"}
```

JSON-encoded, single header, ≤512 bytes (proxy hard-truncates). For multi-suggestion responses we either pick highest-confidence or collapse to a `Link` header with multiple `rel="proxy-mcp-suggestion"` values.

### Trigger

Emit when `scan_and_emit_for_response()` produces ≥1 suggestion AND the caller's per-key flag `mcp_suggestion_emission_enabled` is True (default True — operator can mute per key in dashboard).

### Implementation

- New module `app/mcp_server/suggestion_emit.py`
- Hook in `_compliance_handler` post-response path (right after the existing `X-Compliance-Substitution` header), order: substitution → suggestion → response
- Plain-text fallback for non-JSON-safe values (defensive truncation of `reason`)

### Tests

- Unit: refusal in response → header set with expected JSON
- Unit: no refusal → header absent
- Unit: per-key flag off → header absent even with refusal
- Integration: header round-trips through nginx (smoke env)

### Roll-out

Behavior change is additive (new header). No deploy-blocking risk. Ship to smoke first, then fleet.

## Ship 2 — LMRH-adjacent score + threshold gating

**Scope** ~1 day. The hardest piece is data plumbing, not logic.

### Why a new table, not a new LmrhDim row

`LmrhDim` is a *protocol* table — registers the name + semantics of a routing dimension. It doesn't store per-caller values; those flow through individual request bodies.

Per-caller behavioral scores need a *state* table. New:

```python
class CallerCapabilityScore(Base):
    __tablename__ = "caller_capability_score"
    id = Column(Integer, primary_key=True, autoincrement=True)
    api_key_id = Column(String, ForeignKey("api_keys.id"), nullable=False, index=True)
    suggested_tool = Column(String, nullable=False, index=True)
    score = Column(Float, default=0.0)              # 0.0..1.0
    last_event_at = Column(DateTime, nullable=False)
    decayed_at = Column(DateTime, nullable=False)
    __table_args__ = (UniqueConstraint("api_key_id", "suggested_tool"),)
```

### Score math

- Each new `mcp_capability_suggestion` row for (key, tool) adds `+0.2` to score, capped at `1.0`
- Background worker runs every 6h, applies exponential decay `score *= 0.85` per 24h since `last_event_at`, deletes rows below `0.05`
- Threshold for emission: `score ≥ 0.5` (operator-tunable via `system_settings["mcp_suggestion_threshold"]`)

This means a single refusal doesn't trigger the back-pressure header; **a pattern over multiple requests does**. Tunable; the default keeps noise out.

### Ingest hook

Capability scout's `emit_suggestions()` already writes the activity_log row. Add a sibling call to `_update_caller_score(api_key_id, suggested_tool)`. Cheap upsert.

### Tests

- Unit: 3 refusals over 1h → score 0.6, header fires
- Unit: 1 refusal then decay 7d → score < threshold, header silent
- Unit: operator threshold flip → emission switches

## Ship 3 — Implicit accept + per-key allow-list flip

**Scope** ~1 day. The compliance/audit half is the careful piece.

### Accept header

Caller's next `/v1/messages` request includes:

```
X-Proxy-Accept-MCP: tool=read_xlsx_to_markdown,ttl_hours=168
```

(Note: ASCII-comma-separated; not JSON. Some HTTP middleware mangles JSON-in-header.)

### Server behavior on accept

1. Validate `tool` is a known MCP tool name (whitelist match — reject unknown names with a `Warning:` response header rather than a hard 4xx, so a stale suggestion in a long-running session doesn't error the call)
2. Validate `ttl_hours` ∈ [1, 720] (1 hour to 30 days); clamp out-of-range
3. Update the caller's ApiKey: append `tool` to `mcp_tools_allow` JSON list if absent, set `mcp_tools_allow_until[tool] = now + ttl_hours`
4. Write a `compliance_policy_change` audit row, scope=`"api_key"`, target=key.id, reason=`"mcp_tool_adopted_via_accept_header"`, before/after states fully populated
5. Continue with the request normally; the newly-allowed tool now goes through Path B injection on this same call

### Why a `Warning:` header for unknown tools instead of 4xx

A bot reading the suggestion header from a previous turn could be replaying an accept after the operator removed the tool from the catalog. Hard-failing the call to penalize the bot for a stale suggestion is bad UX. A `Warning:` is RFC 7234 compliant, dev-visible, and the bot's actual request still gets processed.

### TTL expiry

A new worker (or extend existing `prune.py` sweep) checks `mcp_tools_allow_until` per key and removes expired entries from the allow-list. Writes a sibling `compliance_policy_change` row with scope=`"api_key"`, reason=`"mcp_tool_ttl_expired"`.

### Tests

- Unit: accept header with known tool → allow-list updated, audit row written
- Unit: accept header with unknown tool → `Warning:` header in response, allow-list untouched, no audit row
- Unit: TTL expiry sweeper removes entry, writes audit
- Integration: end-to-end on smoke: refuse → see suggestion → next call sends accept → tool is auto-injected on that very call

## Compliance / audit considerations

The closed loop adds two new compliance events:

1. **Tool adopted via accept header** — bot opted in. Scope `api_key`, reason "mcp_tool_adopted_via_accept_header", capture the prior + new `mcp_tools_allow` for both before/after states.
2. **Tool TTL expired** — system removed, no bot intent involved. Scope `api_key`, reason "mcp_tool_ttl_expired".

Both belong in `compliance_policy_changes` (not `compliance_events`) since they record state changes to ApiKey policy rather than per-request events. This matches the existing pattern for retention edits.

Add to the compliance taxonomy doc (`docs/compliance-taxonomy-v5.0.0.md`).

## Risk + rollback

- **Header pollution** — if a runaway scout fires for every response, the header would clutter all responses. Mitigation: per-key emission flag (Ship 1) + threshold gating (Ship 2). Worst case operator disables emission via system_setting.
- **Auto-adoption of a malicious tool** — the only tools eligible are ones already in the proxy's catalog (operator-curated). A bot can't accept a tool that doesn't exist on the proxy side. Allow-list is per-key, not global.
- **TTL expiry surprises bot teams** — first emission of TTL expiry should be loud (memo team + add to status page). After that it's expected behavior.
- **Rollback path** — revert single setting `mcp_suggestion_emission_enabled=false` mutes Ship 1+2 fleet-wide. Ship 3's adoption handler is gated on emission having happened first, so muting upstream silences it too. The data tables persist but become read-only.

## Addendum — 2026-06-29: findings from upstream review of ccproxy

**Source:** `starbaser/ccproxy` (2026-06-29 audit). Their MCP server at `src/ccproxy/mcp/server.py` exposes flow-inspection tools and bridges server-side observations into the LLM context via FastMCP's `Context.info()` mechanism, which emits `notifications/message` events interleaved into the streaming POST response of an MCP tool call. Their `src/ccproxy/mcp/buffer.py` implements a `NotificationBuffer` with TTL + overflow markers keyed by task_id.

**What this changes for our v5.10 design:**

### 1. New wire-format option: MCP-native notifications

ccproxy demonstrates that the existing MCP streamable-HTTP transport already has a notification channel — `notifications/message` per the MCP spec. Callers with a live /mcp connection (our Path A users) can receive proxy-side observations through the protocol they already speak.

This was missing from my original protocol-surface options table. Adding it:

| Channel | When usable | Pros | Cons |
|---|---|---|---|
| `X-Proxy-MCP-Suggestion` header (JSON) | Every response | Simplest; parseable | Header bloat; cap-aware clients only |
| `Link: <...>; rel=...` header | Every response | RFC 5988 standard | Less semantic; URL-based, awkward for inline data |
| SSE `event: proxy_signal` in streamed body | Streaming only | Real-time; same channel as content | Caller must parse SSE event types |
| **MCP `notifications/message`** | Caller has open /mcp conn | Protocol-correct; MCP clients render natively | Path A only |
| ❌ Insert into assistant content | Never | — | Breaks compliance audit + content integrity |

**Recommended split:** Ship 1 emits BOTH the header AND, when the caller has a live /mcp connection, an MCP notification. Cost is minimal (the notification path adds ~30 LOC reusing existing FastMCP infra) and we cleanly cover both audiences without picking one over the other.

### 2. Caller buffer pattern

Their `NotificationBuffer` keyed by task_id with TTL + overflow markers is a useful reference for our `CallerCapabilityScore` table. Specifically:

- **Overflow marker pattern** — when a buffer hits its cap, replace the oldest entries with a single `{"type": "ccproxy_buffer_overflow", "dropped_events": N}` synthetic record so the consumer can see they're missing data. Applies cleanly to our score table: if a key accumulates >100 distinct refusal patterns we can compact into a single `overflow_compacted: true` marker rather than evicting silently.
- **TTL with last_seen** — they touch `last_seen` on every append; we already plan a decay worker but should pin the TTL semantics: 7-day inactivity → drop the score record entirely (vs. just decay to zero). Avoids unbounded growth of `caller_capability_score` from one-off keys.

### 3. Static bearer token verifier

Their `_StaticTokenVerifier` (server.py:30-46) wraps a single expected token for the MCP server — same pattern we use today for /mcp via per-key auth. Validates our existing approach; no change needed.

### Open question for operator decision

**Should v5.10 Ship 1 also emit MCP `notifications/message` when the caller has an open /mcp connection?**

Saying yes: ~30 LOC; uses our existing FastMCP infra; protocol-correct for Path A users. Saying no: skip; revisit in Ship 4 alongside SSE event type. Recommendation: **yes** — cleaner for Path A users with no downside for header-based consumers.

### What was NOT borrowed from ccproxy

- **DAG-driven pipeline** (their architecture) — deferred as separate refactor, not v5.10-relevant.
- **`/mcp` flow-inspection tools** — their tools (flow listing, body inspection, shape manipulation) are for *their* `flows`/`mitmweb` capture surface, not our compliance-audit-event surface. Different problem.
- **WireGuard namespace transport** — entirely orthogonal.
