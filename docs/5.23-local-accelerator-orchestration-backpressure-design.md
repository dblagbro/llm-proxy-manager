# v5.23 — Local Accelerator Orchestration + Resource Back-Pressure

> Status: **design draft, 2026-08-17** · Owner: Devin Blagbrough
> Reference hardware: Dell Pro Max 16 (Ultra 7 265H / 32 GB / RTX PRO 500 6 GB)
> Companion workstream name: **Back-Pressure** (see §10 PR slices)

## 0. TL;DR

llm-proxy already knows *which provider* should serve a request. It does not know
*whether the machine can physically serve it right now*. On a hosted provider that
gap is invisible — the vendor absorbs it. On a single-GPU laptop with one 6 GB card
and 32 GB of system RAM, that gap is the whole problem: loading a ~19 GB MoE takes
30–90 s, evicts the model that was already resident, and can push the box into swap.

This document specifies a **Local Accelerator Manager (LAM)**: a resource-aware
admission layer that treats the local GPU as an exclusive, stateful resource with a
residency lifecycle, and that answers every request with one of *serve now*, *wait
this long*, or *no* — never with a silent 90-second stall or an OOM.

Two things are deliberately separated here, because the repo already uses the term
"back-pressure" for something else:

- **`docs/5.10-mcp-backpressure-design.md`** — back-pressure as *capability signalling*
  (telling a caller it should adopt an MCP tool). Unrelated to this document.
- **This document** — back-pressure as *resource admission control* (refusing or
  delaying work that would exhaust VRAM/RAM). New concern, new module.

---

## 1. Problem

The proxy's local-inference story today assumes an Ollama endpoint behaves like a
hosted API: stateless, always-warm, horizontally elastic. It is none of those.

1. **One GPU, one model.** With `OLLAMA_MAX_LOADED_MODELS=1`, requesting model B
   evicts model A. The proxy neither triggers nor observes that eviction; it just
   sees a request that takes 60 s instead of 2 s.
2. **Cold load exceeds every deadline in the codebase.** `Provider.timeout_sec`
   defaults to `30` (`app/models/db_provider.py:39`) and is handed to litellm as the
   call timeout (`app/routing/litellm_binding.py:300`). A 30–90 s cold load of a 19 GB
   MoE blows that deadline, litellm raises a timeout, and
   `circuit_breaker.classify_error` opens the breaker on the *only* local provider.
   **Out of the box, the first heavy request bricks the local route.**
3. **RAM, not VRAM, is the binding constraint.** See §2. Admission that only checks
   VRAM will happily accept a request that drives the box into pagefile thrash, which
   presents as a hang, not an error.
4. **No queue, no hysteresis.** Alternating inner-loop and agentic requests would
   thrash 7B↔30B indefinitely, spending more wall-clock loading than generating.
5. **Nothing to tell the client.** There is no way to say "this will take 60 s, hold"
   or "not now, retry in 20 s". The only vocabulary the proxy has for a busy local
   backend is a timeout.

## 2. Reference hardware and why the numbers matter

| Resource | Value | Consequence |
|---|---|---|
| GPU | RTX PRO 500 Blackwell, **6113 MiB** | Holds attention + KV only for the 30B; observed idle-parked at 5.5/6.0 GB, so sessions must start near-empty |
| GPU power | TGP ~40 W (65 W max) | Sustained tok/s is thermally limited; not a correctness issue, but load times vary run to run |
| CPU | Ultra 7 265H, 16c/16t, **no SMT** | Expert FFN compute for MoE offload; AVX2 + DDR5-5600 make offload viable |
| RAM | **32 GB DDR5** | The real ceiling — see arithmetic below |
| NPU | ~13 TOPS | Unused; explicit non-goal (§5) |

**The RAM arithmetic that drives this design.** For `qwen3-coder:30b-a3b` at Q4_K_M
(~18.6 GB) with expert offload and q8 KV at 32k context:

```
GPU  : non-expert weights ~2.5-3.0 GB  +  KV q8 @32k ~1.5-2.0 GB   ≈ 4.5-5.0 GB  (of 6.0)
RAM  : expert weights            ~15-16 GB
     + OS + Cursor + browser      ~8-12 GB
     ------------------------------------
     total                        ~23-28 GB  (of 32)
```

That fits, but with single-digit gigabytes of margin. Open a few more Chrome tabs and
the box pages. **This is why admission control must gate on available RAM, not just
VRAM** — VRAM exhaustion produces a clean CUDA OOM the breaker can classify, whereas
RAM exhaustion produces swap, which produces a 10× slowdown that is indistinguishable
from a hung request.

**Load-time envelope — be honest with clients.** Ollama mmaps the GGUF, so an unloaded
model's pages linger as reclaimable page cache and a fast reload is *possible*. But
with 32 GB total and an 18.6 GB file, there is not enough headroom to guarantee those
pages survive a stint running the 7B alongside the OS and an IDE. **Design for cold:
30–90 s.** Treat a warm reload (5–15 s) as a bonus the client must never depend on.

| Transition | Planning envelope |
|---|---|
| `coder` (7B, 4.7 GB) cold load | 5–12 s |
| `qwen3-coder:30b` cold load | **30–90 s** |
| `qwen3-coder:30b` partial-warm reload | 10–40 s (unreliable — do not promise) |
| Explicit unload (`keep_alive: 0`) | 1–3 s |

### Gaps

1. **No resource telemetry.** Nothing reads VRAM, RAM, `nvidia-smi`, or `ollama ps`.
2. **No model lifecycle.** The proxy never loads, unloads, or pins a model. It cannot
   free the GPU before requesting a 19 GB model.
3. **Concurrency limits are per-API-key, not per-resource.** Two keys hitting the same
   local GPU are unbounded with respect to each other.
4. **No queue.** The only outcomes are "dispatch immediately" or "reject".
5. **`timeout_sec` default of 30 s is incompatible with local heavy models** (§1.2).
6. **Ollama capability inference is wrong for modern local models.**
   `app/routing/capability_inference.py:55` sets `native_tools = False` for every
   `ollama` provider. Since v4.1.1 that no longer *skips* the provider, but it does
   engage prompt-based tool **emulation** (`tool_emulation_engaged`) instead of using
   Qwen3-Coder's genuine tool-calling — measurably worse for OpenCode's agentic loop.
   Also `PROVIDER_DEFAULT_MODELS["ollama"] = "llama3"` (`litellm_binding.py:229`).
7. **No Windows support.** `DATABASE_URL` defaults to the POSIX path
   `/app/data/llmproxy.db`; deployment docs are Docker-and-nginx only. Nothing is
   *hostile* to Windows, but nothing is tested there either. See §9.

## 4. Goals

- **G1** Never accept work the machine cannot physically complete.
- **G2** Never silently stall. Every slow path is either an explicit wait with an
  advertised duration, or a refusal with `Retry-After`.
- **G3** One resident local model at a time, enforced by the proxy, not hoped for.
- **G4** Swapping 7B↔30B costs 30–90 s, so **do not do it often**. Hysteresis is a
  correctness requirement, not a tuning knob.
- **G5** Full observability: queue depth, load seconds, VRAM/RAM, reject reasons.
- **G6** Degrade to today's behavior when disabled. `LOCAL_ACCEL_ENABLED=false` must
  be a complete no-op.

## 5. Non-goals

- **Splitting one GGUF across NVIDIA + Arc + NPU.** One GPU done well beats three
  compute devices contending for one memory bus.
- **Using the NPU for these LLMs.** No path through llama.cpp/Ollama reaches it, and
  it would be slower than the dGPU if one existed.
- **Public-tunnelling Ollama so Cursor can reach it.** Out of scope and a security
  liability.
- **Multi-GPU / multi-node scheduling.** LAM manages the accelerators of *one* host.
- **Replacing the circuit breaker.** LAM prevents resource failures; the breaker still
  handles upstream failures.

## 6. Design

### 6.1 Component

New package `app/resources/`:

```
app/resources/
  __init__.py
  probe.py        # telemetry: nvidia-smi/NVML, psutil RAM, GET /api/ps
  residency.py    # per-accelerator state machine + exclusive lock
  admission.py    # watermark evaluation -> Admit | Queue | Reject
  queue.py        # bounded FIFO with max-wait and cancellation
  lifecycle.py    # load / unload / pin against the Ollama backend
  errors.py       # ResourceUnavailable, LoadTimeout, QueueFull
```

The backend is an interface (`lifecycle.LocalBackend`) with `OllamaBackend` as the
first implementation, so llama.cpp `llama-server` and vLLM can follow without
touching admission logic.

### 6.2 Residency state machine

One instance per accelerator (here: exactly one).

```
                   ┌──────────────────────────────────────────┐
                   ▼                                          │
  ┌───────┐  admit(m)   ┌──────────┐  load ok   ┌────────┐    │ idle > dwell
  │ EMPTY │────────────▶│ LOADING  │───────────▶│ WARM   │────┘ (or evict for m')
  └───────┘             │  (m)     │            │  (m)   │
      ▲                 └──────────┘            └────────┘
      │                       │ load fail/timeout    │ admit(m') where m' != m
      │                       ▼                      ▼
      │                 ┌──────────┐            ┌──────────┐
      └─────────────────│  FAILED  │            │ DRAINING │  wait for in-flight
        cooldown        └──────────┘            └──────────┘  then unload -> EMPTY
```

Invariants:

- **At most one model in `WARM` or `LOADING` per accelerator.** Enforced by an
  `asyncio.Lock` held across the whole load, not just the state mutation.
- **`DRAINING` blocks new admissions for the outgoing model** but lets in-flight
  requests finish. No request is ever killed to make room.
- **A `LOADING` transition is announced before it starts** (provider marked
  `auto_skip_until = now + predicted_load`, reason `"loading <model>"`), so concurrent
  requests see a truthful state rather than racing into the same load.
- **Pre-flight unload is explicit.** Before loading a heavy model, LAM issues
  `POST /api/generate {"model": <outgoing>, "keep_alive": 0}` and waits for
  `GET /api/ps` to confirm eviction. Relying on Ollama's implicit eviction hides the
  cost inside the load and makes the timeout unattributable.

### 6.3 Task-class routing

Classification, in precedence order — first match wins:

1. **Explicit LMRH hint** (authoritative):
   `LLM-Hint: accelerator=local, residency=warm;require`
2. **Explicit model / logical alias.** `coordinator-local` and `coordinator-fast`
   already exist (`aliases.py:23-37`). Add `coordinator-local-heavy`.
3. **Tool use present** (`has_tools`) → agentic → heavy class.
4. **Estimated input tokens** via the existing `_estimate_input_tokens()`
   (`_request_pipeline.py:34`) — above `LOCAL_ACCEL_HEAVY_TOKEN_THRESHOLD`
   (default 6000) → heavy.
5. **Client role hint.** OpenCode's `small_model` vs `model` distinction arrives as
   two different model names; map them in the alias table.
6. **Default** → inner-loop.

Two new LMRH dimensions, registered through the existing self-extension mechanism
(`POST /lmrh/register`, `docs/draft-blagbrough-lmrh-00.md`) rather than a bespoke
header:

| Dim | Values | Meaning |
|---|---|---|
| `residency` | `warm` \| `any` \| `cold-ok` | `warm;require` → 503 rather than trigger a load. The key primitive for latency-sensitive callers. |
| `accelerator` | `local` \| `remote` \| `<id>` | Pin to (or away from) host-local compute. |

`residency=warm;require` is what makes an editor autocomplete path safe: it can never
accidentally trigger a 90-second load.

### 6.4 Hysteresis — the anti-thrash rules

All four apply simultaneously; any one can defer a swap.

| Rule | Default | Behavior |
|---|---|---|
| **Dwell time** | `LOCAL_ACCEL_DWELL_SEC=90` | A newly-loaded model cannot be evicted for this long. Requests for the other class queue or are rejected with `Retry-After = remaining dwell`. |
| **Cooldown** | `LOCAL_ACCEL_COOLDOWN_SEC=30` | After any unload, no new load for this long. Absorbs alternating bursts. |
| **Sticky session** | `LOCAL_ACCEL_STICKY_TTL_SEC=600` | Requests carrying the same session/conversation id keep affinity to the model that served the first turn. Reuses the existing conversation-id plumbing (`CONVERSATION_ID_REQUESTS_TOTAL`, `app/observability/prometheus.py:134`). |
| **Swap budget** | `LOCAL_ACCEL_MAX_SWAPS_PER_HOUR=6` | Hard ceiling. On breach, the *minority* class is refused with `503 thrash_guard` until the window rolls. Emits a loud operator alert — sustained breach means the workload genuinely needs two machines. |

Escape hatch: `LLM-Hint: residency=cold-ok, effort=high;require` bypasses dwell (not
the swap budget) for a deliberate one-off heavy job.

### 6.5 Admission control

Evaluated **before** the model is loaded and before `select_provider` dispatches.

```python
# app/resources/admission.py  (sketch)
async def evaluate(req: AdmissionRequest) -> Decision:
    acc = residency.get(req.accelerator_id)
    need = estimate(req.model)          # from ModelResourceProfile

    if acc.state is WARM and acc.model == req.model:
        if acc.in_flight >= need.max_concurrency:
            return Queue(reason="model_busy", eta=acc.p95_request_sec)
        return Admit()                                    # fast path, no probes

    if req.requires_warm:                                 # residency=warm;require
        return Reject(503, "residency_not_warm", retry_after=acc.eta_warm_sec())

    if acc.state is LOADING:
        return Queue(reason="model_loading", eta=acc.load_eta_sec())

    snap = await probe.snapshot()                         # cached, TTL 2s
    if snap.vram_free_mb < need.vram_mb + VRAM_HEADROOM_MB:
        if not acc.can_evict_now():                       # dwell / in-flight
            return Reject(503, "vram_exhausted", retry_after=acc.dwell_remaining_sec())
    if snap.ram_available_mb < need.ram_mb + RAM_RESERVE_MB:
        return Reject(503, "ram_watermark", retry_after=30)
    if snap.swap_rate_pages_sec > SWAP_ALERT_PAGES_SEC:
        return Reject(503, "host_swapping", retry_after=60)
    if queue.depth() >= QUEUE_MAX:
        return Reject(429, "queue_full", retry_after=queue.eta_sec())
    if not acc.swap_budget_ok():
        return Reject(503, "thrash_guard", retry_after=acc.swap_window_remaining_sec())

    return Queue(reason="needs_load", eta=need.load_eta_sec())
```

**Watermarks** (defaults tuned for the reference hardware):

| Setting | Default | Rationale |
|---|---|---|
| `LOCAL_ACCEL_VRAM_HEADROOM_MB` | `512` | Leaves room for CUDA context growth and desktop compositing. |
| `LOCAL_ACCEL_RAM_RESERVE_MB` | `6144` | OS + IDE + browser floor. The single most important number on a 32 GB box. |
| `LOCAL_ACCEL_SWAP_ALERT_PAGES_SEC` | `2000` | Detects the thrash spiral before it becomes a "hang". |
| `LOCAL_ACCEL_QUEUE_MAX` | `4` | Bounded. Never unbounded. |
| `LOCAL_ACCEL_QUEUE_MAX_WAIT_SEC` | `120` | Must exceed the p95 cold load (90 s) or heavy requests can never succeed. |
| `LOCAL_ACCEL_LOAD_TIMEOUT_SEC` | `180` | Hard ceiling on a single load attempt → `FAILED` + cooldown. |

`ModelResourceProfile` is a new table (`vram_mb`, `ram_mb`, `load_p50_sec`,
`load_p95_sec`, `max_concurrency`, `context_cap`), seeded from a static registry and
then **continuously refined from observed loads** — after a handful of real loads the
ETAs are measured, not guessed.

### 6.6 Queue

Bounded FIFO per accelerator. Not a work queue — a **waiting room** for requests that
have already been admitted in principle.

- Depth capped at `QUEUE_MAX`; overflow → `429 queue_full`.
- Each entry carries a deadline (`min(QUEUE_MAX_WAIT_SEC, client_timeout)`); expiry →
  `503 queue_timeout`.
- Client disconnect cancels the entry (`await request.is_disconnected()`), so an
  abandoned OpenCode request does not hold a slot.
- Priority: inner-loop outranks heavy *only* when the inner-loop model is already
  `WARM` — cheap requests jump a queue they don't perturb, but never starve a heavy
  request that has already triggered a load.

### 6.7 Wire contract

**Response headers on every local-route response:**

```
X-LLMP-Accelerator: local-gpu-0
X-LLMP-Residency: warm | cold | loading
X-LLMP-Model-Resident: qwen2.5-coder:7b
X-LLMP-Queue-Depth: 0
X-LLMP-Load-Wait-Ms: 0
```

**Refusals** — structured JSON, OpenAI-shaped `error` object so existing SDKs surface
it, plus the machine-readable extensions:

```json
{
  "error": {
    "message": "Local accelerator cannot admit this request: 18.6 GB model needs 21.0 GB RAM, 9.2 GB available.",
    "type": "resource_unavailable",
    "code": "ram_watermark",
    "param": null
  },
  "llmp": {
    "accelerator": "local-gpu-0",
    "resident_model": "qwen2.5-coder:7b",
    "requested_model": "qwen3-coder:30b",
    "retry_after_sec": 30,
    "queue_depth": 2,
    "remedy": "Close memory-heavy applications, or request residency=warm to use the resident model."
  }
}
```

| Condition | Status | `Retry-After` |
|---|---|---|
| Another model loading | **503** `model_loading` | predicted remaining load |
| VRAM insufficient, cannot evict (dwell) | **503** `vram_exhausted` | dwell remaining |
| RAM below watermark | **503** `ram_watermark` | 30 |
| Host swapping | **503** `host_swapping` | 60 |
| Swap budget exhausted | **503** `thrash_guard` | window remaining |
| Queue full | **429** `queue_full` | queue ETA |
| Queue wait exceeded | **503** `queue_timeout` | 0 (retry at will) |
| `residency=warm;require` unmet | **503** `residency_not_warm` | ETA to warm |

**503 vs 429 rule:** 429 means *you* sent too much (client-shaped, client should slow
down). 503 means *the host* cannot serve right now (server-shaped, retry unchanged).
Both always carry `Retry-After`.

**202 + poll for long loads.** When the predicted load exceeds
`LOCAL_ACCEL_SYNC_WAIT_MAX_SEC` (default 20 s) and the client advertises support via
`X-LLMP-Async: allow`, LAM creates a Run through the existing runtime and returns
`202` with `{"run_id": ..., "poll": "/v1/runs/{id}/events"}`. This reuses the whole
`app/runs/` state machine, SSE broker, and idempotency layer rather than inventing a
second async surface. A new `model_loading` event carries `{progress_pct, eta_sec}`.

### 6.8 Streaming rules

- **A load is never initiated mid-stream.** Admission runs to completion before the
  first upstream byte. Once streaming starts the model is pinned for that request's
  duration (`in_flight` count blocks eviction).
- **A `DRAINING` model finishes its open streams.** Eviction waits for `in_flight == 0`
  or `DRAIN_TIMEOUT_SEC` (default 300), whichever comes first.
- **Loads emit heartbeats.** When a streaming request must wait for a load, LAM emits
  SSE comment frames (`: llmp-loading eta=47s`) every 5 s so proxies and clients don't
  time out an idle connection. Anthropic-shaped streams reuse the existing
  `content_block` synthesis path from v4.4.5.

## 7. Failure modes

| Failure | Detection | Response |
|---|---|---|
| Ollama not running | Probe connection refused | Accelerator `FAILED`; provider `auto_skip_until` set; local routes 503 with a clear remedy. Do **not** trip the 24 h auth breaker. |
| Load exceeds `LOAD_TIMEOUT_SEC` | Timer in `lifecycle.load()` | Force unload, `FAILED` + cooldown, 503 to all queued waiters. Record `load_seconds{outcome="timeout"}`. |
| CUDA OOM during load | Ollama error string | Shrink context cap one step (64k→32k→16k), retry **once**, then `FAILED`. Persist the working cap to `ModelResourceProfile`. |
| Host enters swap mid-generation | Probe swap rate | Do not kill the in-flight request. Stop admitting; raise the RAM watermark for the rest of the window; alert. |
| Model evicted externally (operator ran `ollama stop`) | `GET /api/ps` disagrees with LAM state | Reconcile to observed truth on every probe tick. Observed state always wins over believed state. |
| Proxy restarts with a model resident | Startup reconciliation | Adopt the observed resident model as `WARM` rather than assuming `EMPTY`. Mirrors the existing Runs recovery sweep. |
| Queue entry's client vanishes | `request.is_disconnected()` | Cancel, free the slot, `admission_total{decision="cancelled"}`. |
| Two requests race for the same load | `asyncio.Lock` in `residency` | Loser waits on the same load future — one load, two satisfied requests. Never two concurrent loads. |
| `nvidia-smi` / NVML unavailable | Probe raises | Fall back to `GET /api/ps` size accounting + configured `VRAM_TOTAL_MB`. Log once, degrade, don't crash. |

## 9. Windows notes (first-class, not an afterthought)

The reference hardware runs Windows 11. Today's deployment story is Docker + nginx on
Linux; the reference deployment for this feature is **native uvicorn on Windows**.

| Concern | Detail |
|---|---|
| Database path | `DATABASE_URL` defaults to `sqlite+aiosqlite:////app/data/llmproxy.db` — a POSIX path. Needs a documented Windows override (`sqlite+aiosqlite:///C:/Users/<user>/.llm-proxy/llmproxy.db`) and directory auto-creation. |
| VRAM telemetry | Prefer **NVML via `pynvml`** over shelling to `nvidia-smi.exe` — no subprocess per probe, no PATH assumptions, works identically on both platforms. Keep `nvidia-smi` as fallback. |
| RAM / swap | `psutil.virtual_memory()` is cross-platform. Pagefile stats need `psutil.swap_memory()`; `sin`/`sout` are **not populated on Windows**, so derive pressure from `GetPerformanceInfo` / WMI `Win32_PageFileUsage` instead of assuming POSIX counters. |
| No `os.getloadavg()` | Not implemented on Windows. Any CPU-pressure signal must use `psutil.cpu_percent()`. |
| Event loop | Windows defaults to `ProactorEventLoop`. Subprocess handling differs; another reason to prefer NVML over subprocess probing. |
| Ollama lifecycle | Use the **HTTP API**, not the `ollama` CLI: `POST /api/generate {"model": m, "keep_alive": 0}` to unload and `GET /api/ps` to verify. No PATH dependency, no shell, same code on both platforms. |
| Path separators | New code must use `pathlib`, never string-joined `/`. |
| CI | Add a `windows-latest` job to `.github/workflows/ci.yml` running `tests/unit`. Cheap, and it prevents POSIX-only assumptions from creeping back in. |

## 10. Acceptance tests

Written as the operator-verifiable behaviors a reviewer should demand.

1. **No breaker trip on cold load.** With `timeout_sec=240`, a first request to a
   cold 30B returns 200 and the circuit breaker stays closed.
2. **Exclusive residency.** Concurrent requests for 7B and 30B result in exactly one
   `LOADING` transition; `ollama ps` never shows two resident models.
3. **Pre-flight unload.** Loading the 30B while the 7B is resident produces an
   observable unload before the load, and `llmp_local_model_unload_seconds` records it.
4. **RAM watermark refusal.** With available RAM artificially held below
   `need.ram_mb + RAM_RESERVE_MB`, a heavy request returns `503 ram_watermark` with
   `Retry-After` — and the host never enters swap.
5. **Bounded queue.** With `QUEUE_MAX=4`, the 5th concurrent heavy request returns
   `429 queue_full`. Queue depth never exceeds 4.
6. **Anti-thrash.** Alternating inner-loop/heavy requests for 10 minutes produce
   ≤ `MAX_SWAPS_PER_HOUR` swaps; the minority class receives `503 thrash_guard`.
7. **`residency=warm;require` never loads.** With the 7B resident, a heavy request
   carrying that hint returns `503 residency_not_warm` immediately and no load starts.
8. **Streams are not interrupted.** A 30B load requested during an active 7B stream
   waits; the 7B stream completes without truncation.
9. **State reconciliation.** An out-of-band `ollama stop` is reflected in
   `GET /api/local/accelerators` within one probe interval.
10. **Disabled is a no-op.** With `LOCAL_ACCEL_ENABLED=false`, the full existing test
    suite passes unchanged and no new code path executes.
11. **Windows parity.** `tests/unit` passes green on `windows-latest`.

## 12. Open questions for the maintainer

1. **Does LAM own the accelerator, or observe it?** This spec assumes *owns* (the
   proxy issues loads and unloads). A weaker "observe and refuse" variant is ~40% of
   the work and still delivers the back-pressure contract, but leaves swap timing to
   Ollama's implicit eviction — which is where the unattributable latency lives.
2. **Cluster semantics.** LAM state is inherently per-host. Should
   `/api/local/accelerators` participate in `/cluster/sync` as read-only telemetry so
   the fleet view shows local capacity, or stay strictly node-local?
3. **Is `503` correct for `thrash_guard`?** It is arguably a client-shaped problem
   (the caller is alternating classes). `429` would tell a well-behaved client to back
   off. Current draft chooses 503 because the *host* is the constrained party.
4. **Default posture.** `LOCAL_ACCEL_ENABLED=false` by default is safest, but means
   the feature is invisible until opted in. Enable by default when exactly one
   self-hosted provider is configured?
