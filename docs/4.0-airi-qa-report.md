# AIRI v4.0 — Full QA Report

**Date:** 2026-05-16
**Branch:** `4.0-airi`
**Build under test:** llm-proxy2 core v3.10.17 + AIRI v4.0 (milestones 1–5)
**Verdict:** ✅ **39 / 39 live checks passed** — go-live ready, pending the
operator's release decision.

---

## 1. Scope

AIRI (AI Router Interface) is the conversational UI for the AI Provider
Supervisor — a chat panel on the Routing/LMRH page. This QA exercises all five
build milestones end-to-end:

1. Read-only chat + grounded answers
2. Rules layer + named rule-sets
3. Propose / dry-run / apply / reject / revert + safety guards
4. Scheduled rules + monitors + deterministic evaluator + kill switch
5. Conversation history + cross-user search

## 2. Method

- **Environment:** a throwaway Docker container (`llm-proxy2:airi-smoke`) built
  from the `4.0-airi` branch, on an isolated copy of the production database
  (10 providers, real settings). `AIRI_ENABLED=true`, cluster disabled.
- **Real LLM:** every chat turn runs the AIRI agent loop against the proxy's
  own `/v1/messages` — a real model, real tool calls, real proposals.
- **Two users** (`dblagbro`, `admin`) to verify cross-user behaviour.
- The container and the DB copy were destroyed after the run (they hold
  production credentials).
- The production fleet stayed on v3.10.17 throughout — nothing was deployed.

In addition to the live pass, the deterministic logic is covered by the unit
suite: **2071 tests passing, 58 of them AIRI-specific** (M1×11, M2×9, M3×15,
M4×11, M5×12).

### Cross-cutting — stat hygiene
AIRI made ~30 internal LLM calls during the QA. All were tagged
`X-Internal-Source: airi` and recorded as internal in the activity log — per
BUG-026 they are excluded from provider error-rate stats, so AIRI's own traffic
never pollutes the metrics it reasons about.

## 4. Safety properties verified

- **No recurring LLM mutation** — the evaluator loop ran a conditional rule with
  zero LLM calls (Group D live-fire).
- **Two-stage commit** — every mutation is a pending proposal first; applying is
  a separate explicit step (Group C).
- **Blast-radius cap** — at most one change auto-applies per turn; a bulk
  destructive request produced pending proposals only (Group C adversarial).
- **Rule-set caps** — an over-large priority change was clamped to the active
  rule-set's `max_priority_delta` (Group C).
- **Last-provider invariant** — `apply_proposal` refuses to disable the last
  enabled provider (unit-tested; the adversarial run left all 10 enabled).
- **Kill switch** — automation is globally pausable and fail-safe off on restart
  (Group D).
- **Reversibility** — every applied change snapshots prior state for one-click
  revert (Group C).

## 5. Caveats / known limitations

1. **Frontend not browser-tested.** The React UI compiles clean (`tsc`
   no-errors) and all backend endpoints it calls are verified here, but no
   automated browser/Playwright run was performed against the AIRI panels. A
   manual UI walkthrough is recommended before release.
2. **Per-user notification preferences** (design §9) are **deferred to 4.0.1**
   by operator decision. M4's notifier emails the configured alert recipients
   with deep links; per-operator opt-in/out is not in v4.0.0.
3. **Loaded historical conversations** render past proposals as plain assistant
   text, not interactive cards (the live Changes panel handles proposals).
4. Cross-user search uses term-AND `LIKE` matching (no FTS5) — adequate at
   operator-chat scale.

## 6. Conclusion

All five milestones pass a full live QA: **39/39 checks**, on top of 2071
green unit tests and per-milestone smoke tests. The safety model — two-stage
commit, caps, per-turn blast radius, the deterministic no-LLM evaluator, the
kill switch, and reversibility — held under adversarial input.

AIRI v4.0 is recommended **go-live ready** for the v4.0.0 release, subject to:
a manual UI walkthrough (caveat 1) and the operator's release decision. The
feature ships behind the `airi_enabled` flag (default off).
