# AIRI — AI Router Interface — v4.0 design

**Status:** design agreed 2026-05-16 (operator + llm-proxy2 session). Implementation
not yet started. Ships as **v4.0.0**; patches `4.0.1+`; voice is **v4.1**.

**Pronounced** "Airy". Voice input (v4.1) uses "Airy" as the wake word; the
assistant self-identifies as Airy.

---

## 1. What AIRI is

AIRI is the **conversational UI for the existing AI Provider Supervisor**
(`app/monitoring/ai_provider_supervisor.py`) — *not* a new agent. Same AI, same
decision engine. AIRI adds, on the proxy's **Routing / LMRH** page:

- a chat panel to talk to the Supervisor in plain English;
- the ability to **edit the Supervisor's rules** conversationally;
- named **rule-set** save / restore (`Default`, "Save as X", "Restore X");
- **per-user, cross-user-searchable** chat history;
- proactive **email outreach** with deep links into the (mobile-optimised) UI.

No LLM-gateway competitor ships a conversational config assistant — this is a
genuine differentiator. The mature cohort (Cloudflare Agent Lee, Azure Copilot,
Datadog Bits, Splunk) has converged on one safety contract: **every mutating
action requires an explicit human approval shown as a plain-language summary +
diff before commit.** AIRI adopts that contract; auto-apply (§4) is the
operator's explicit, per-rule choice, not a bypass of it.

## 2. Keystone constraint — no recurring LLM mutation

The operator has lived a runaway control-loop incident; the research surfaced the
canonical disaster ($47k / 11-day agent loop). Therefore:

> An **operator-authored scheduled rule** is compiled — once, by the LLM, with
> operator approval — into a **deterministic** `trigger → condition → action`.
> Its recurring evaluation is plain Python, **no LLM in the loop**. Recurring LLM
> *inference* is permitted only for **read-only monitor-and-report** tasks.

The Supervisor's own LLM-classifier scan loop is unchanged (existing, capped by
`max_priority_delta` / `max_auto_skip_hours`, governed by settings AIRI now
exposes as editable rules). AIRI's *new* scheduled-rule capability never adds a
recurring LLM mutator.

## 3. Architecture

| Component | Notes |
|---|---|
| **Chat panel** | React, atop the Routing/LMRH page; **mobile-responsive from day one** |
| **AIRI endpoint** | `/api/airi/chat`, SSE-streamed, admin-gated |
| **Rules layer** | makes the Supervisor's implicit policy an explicit, editable rule-set |
| **Rule-set manager** | `Default` baseline + named snapshots; save-as / restore / restore-default |
| **Tool catalog** | ~10–12 JSON-schema'd tools; the LLM parameterises, never emits raw config |
| **Dry-run engine** | simulates a proposed rule/change against the last *N* real requests |
| **Conversation store** | per-user history, cross-user full-text searchable |
| **Audit log** | every change: prompt → trace_id → tool call → diff → prior-state snapshot |
| **Notifier** | email-with-deep-link on outage / over-usage / suspicious activity / changes |

**Model fallback (decision #3):** AIRI's own LLM calls route through the proxy's
normal chain *with fallback enabled* (the Supervisor's `classify_with_llm`
already posts to `localhost:3000/v1/messages`, so this is inherited). If
Anthropic is fully down, AIRI keeps working on alternate providers. Only a
total fleet-wide provider outage stops it — unavoidable and acceptable.

## 4. Rules & rule-sets

- **Rule** — an explicit policy item, one of:
  - `threshold` — a tunable governing the Supervisor (e.g. short-window minutes,
    max priority delta, max auto-skip hours);
  - `conditional` — a deterministic `trigger → condition → action`
    (e.g. "provider X 5xx-rate > 5% for 10 min → auto-skip 1h");
  - `monitor` — a read-only recurring check that reports / notifies.
  Each rule carries: **mode** (`suggest` | `auto_apply`), blast-radius cap,
  max-runs-per-window, cooldown, expiry, oscillation state.
- **Rule-set** — a named snapshot of *all* rules. The `Default` rule-set is
  seeded from the Supervisor's current settings. "Save as X" / "Restore X"
  (dropdown) / "Restore default" (button).
- **Auto-apply (decision #2)** is per-rule and conversational — the user tells
  AIRI "auto-apply this" or "just suggest it". Mode does **not** bypass any
  guardrail: dry-run, caps, oscillation breaker, cooldown, audit all still run;
  `auto_apply` only skips the final manual click.

## 5. Safety model

1. Default **suggest**; apply is explicit (a button, or a spoken/typed
   "auto-apply" that sets the rule's mode).
2. **Two-stage commit:** plan → approve plan → concrete diff → approve → apply.
3. **Curated tool catalog** — the LLM never emits free-form config.
4. **Mandatory dry-run** for every mutation — "this rule would have changed
   routing for *N* of the last *M* requests; provider mix X→Y; cost Δ".
5. **No recurring LLM mutation** (§2).
6. **Budget caps** — per-conversation / per-day / per-month token+cost ceilings
   on AIRI's own LLM usage; alert *approaching*, not only *at*.
7. **Oscillation circuit-breaker** — a rule that flips config back and forth
   trips and freezes pending review.
8. **Cooldown windows** — no automated change reacts to a change made within
   the cooldown.
9. **Kill switches** — global "disable AIRI"; "pause all scheduled rules";
   one-click "revert last change" (every applied change snapshots prior state).
10. **Inherits operator permissions only** — admin-gated.
11. **Prompt-injection hardening** — activity-log content, provider error
    strings and model outputs are *untrusted*; quarantine / spotlighting
    pattern; **API keys & HMAC keys never enter AIRI's context**.
12. AIRI's own calls are tagged `X-Internal-Source: airi` so (per BUG-026) they
    never pollute provider stats or the error-rate alert.

## 6. Data model (new tables)

- `airi_ruleset` — id, name (unique), is_default, description, created_by,
  timestamps.
- `airi_rule` — id, ruleset_id, name, kind (`threshold|conditional|monitor`),
  spec (JSON), mode, enabled, blast_radius_cap, max_runs_per_window,
  cooldown_sec, expiry_at, last_run_at, last_action, oscillation_state,
  created_by, created_via_prompt.
- `airi_conversation` — id, user_id, title, timestamps.
- `airi_message` — id, conversation_id, role, content, tool_calls (JSON),
  trace_id, created_at. **Full-text searchable across all users** (decision #5).
- `airi_action` (audit, append-only) — id, ts, user_id, conversation_id,
  trace_id, prompt, tool, params, proposed_diff (JSON), dry_run_result (JSON),
  mode, applied, prior_state_snapshot (JSON), revert_of.

## 7. Tool catalog

**Read** (no confirmation): `get_supervisor_state`, `get_provider_health`,
`get_routing_config`, `get_recent_routing`, `get_rules`, `get_rulesets`,
`explain_routing`, `search_conversations`.

**Mutating** (proposal → dry-run → apply per mode): `propose_rule_change`,
`propose_provider_change` (priority / enable / auto-skip),
`save_ruleset`, `restore_ruleset`, `restore_default_ruleset`,
`schedule_monitor`, `send_notification`.

**Simulation**: `dry_run` — runs a proposed rule/change through
`select_provider(dry_run=True)` against the last *N* requests from
`activity_log`.

The LLM selects + parameterises; deterministic Python performs every mutation.

## 8. Cross-user coordination (decision #5)

Chat history is persistent per user, but **any user can search every user's AIRI
conversations**. Before AIRI proposes a change it surfaces recent related
changes by other users ("dblagbro raised provider X's priority 20 min ago") so
two operators don't make opposing changes blind. The shared history *is* the
change-coordination surface.

## 9. Notifications, mobile, deep links (decision #7)

AIRI proactively emails users — reusing the existing alert/notification infra —
on: outages, routing changes, over-usage, suspicious activity, anything needing
attention. Every email carries a **deep link** to the relevant AIRI
conversation. The **entire UI is mobile-optimised** so an on-the-road operator
taps the link and discusses it on a phone. Per-user notification preferences.

## 10. Scope

**v4.0.0** — chat UI + conversational Supervisor + editable rules + rule-set
save/restore + suggest/auto-apply by request + dry-run + per-user/cross-search
history + email notifications with deep links + mobile-responsive.

**v4.1** — voice input (wake word "Airy"). Distinct capability (speech-to-text);
does not gate 4.0.0.

**Non-goals (v4.0):** whole-app control (page-scoped to Routing — reads broadly,
writes only routing), free-form config editing, AIRI touching API keys /
billing / cluster config.

## 11. Build milestones (dev order — all converge into the 4.0.0 release)

1. **Read-only chat** — panel, SSE endpoint, read tools, `explain_routing`,
   grounded answers. Zero mutation.
2. **Rules layer + rule-sets** — `airi_ruleset` / `airi_rule`, seed `Default`,
   save/restore.
3. **Propose / apply + dry-run** — mutating tools, the dry-run engine, two-stage
   commit, audit log, revert.
4. **Scheduled rules + monitors + email notifications** — deterministic-rule
   compilation, the registry, kill switches, the notifier.
5. **Cross-user history search + mobile polish.**

## 12. Resolved decisions (2026-05-16)

1. `4.0.0` = first complete implementation; `4.0.1+` = patches.
2. Auto-apply vs suggest is per-rule, set conversationally by the user.
3. AIRI's LLM calls use the proxy's fallback chain — survive an Anthropic outage.
4. AIRI is the UI for the AI Provider Supervisor; same AI; adds rules + rule-sets.
5. Persistent per-user history, cross-user searchable.
6. Name: AIRI / "Airy"; voice (v4.1) wake word "Airy".
7. Email outreach with deep links; mobile-optimised UI.
