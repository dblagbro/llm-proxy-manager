# AIRI v4.3 — Voice output (text-to-speech)

Design doc. Source of truth for the v4.3 build. Companion to
`docs/4.0-airi-design.md` (the AIRI design) and `docs/4.2-voice-design.md`
(voice input). Drafted 2026-05-18.

## 1. What v4.3 is

v4.2 gave AIRI **ears** — push-to-talk and the "Airy" hands-free wake word.
v4.3 gives AIRI a **voice**: "Airy" speaks its answers back aloud, so an
operator can hold a hands-free, eyes-free exchange — ask by voice (v4.2),
hear the reply (v4.3).

v4.3.0 ships an **opt-in speaker toggle** in the AIRI chat panel. When it is
on, each completed AIRI assistant message is synthesized to speech and
played. It is **off by default** and **per-message review still stands** —
TTS only reads back what AIRI already wrote; it changes nothing about how
AIRI answers.

## 2. Keystone constraint — speech stays on our infrastructure

Operator-locked rule (`feedback_open_source_only.md`): we own the dependency
chain; no paid SaaS, no third-party dependency for a new component. This is
the same constraint that shaped v4.2.

For **output**, the browser's `speechSynthesis` (Web Speech API) is less
clearly disqualifying than the input side was — local OS voices do not
stream anywhere. But voice quality and availability vary wildly across
browser and OS, some Chrome voices *are* remote, and "Airy" should have one
consistent voice everywhere. So, matching the v4.2 decision, TTS is done
with **self-hosted open-source Piper** (`rhasspy/piper` — a fast neural TTS
that runs on CPU, fully offline). The AIRI response text is sent to the
proxy, synthesized on our own hardware, and the audio is returned and
played; the audio is **never written to disk or the database**. The text
itself is already in the conversation — TTS exposes nothing new.

## 3. Architecture

```
AIRI assistant message (SSE stream completes)
        │  POST /api/airi/speak  { text }
        ▼
   llm-proxy2  (admin + airi_enabled + airi_tts_enabled gated)
        │  POST /speak   (bearer token)
        ▼
   whisper-bridge ──> Piper ──> 16-bit PCM WAV
        │
        └────── audio/wav ◄────── browser plays it (<audio> element)
```

- **`whisper-bridge`** — the existing voice sidecar (already hosts
  `faster-whisper` STT and the Vosk wake-word model) gains **Piper** and one
  voice model. It is now the single voice sidecar for AIRI: STT, wake model,
  and TTS. New route `POST /speak`, guarded by the same shared bearer token.
- **`POST /api/airi/speak`** — a new llm-proxy2 endpoint. Admin-gated,
  `airi_enabled` + `airi_tts_enabled` gated. Accepts `{ "text": ... }`,
  forwards it to the sidecar, streams back `audio/wav`. The text is not
  logged beyond normal request accounting; the audio is never persisted.
- **`AiriChatPanel`** — a speaker toggle beside the mic. When on, a
  completed assistant message is POSTed to `/api/airi/speak` and the
  returned clip is played. A stop control halts playback at any time.

## 4. The whisper-bridge sidecar — adding Piper

- **Stack added:** `piper-tts` (the Python package; bundles the ONNX
  runtime). No system packages beyond what the image already has.
- **Voice model:** one Piper en-US voice baked into the image at build
  time — default `en_US-amy-medium` (a clear, natural medium-quality voice;
  an `.onnx` model + `.onnx.json` config, ~60 MB). Configurable via
  `PIPER_VOICE`. Build-time fetch only — the running container makes no
  external call, exactly like the Whisper and Vosk models.
- **Route:** `POST /speak` — JSON `{ "text" }` → `audio/wav` (16-bit PCM,
  the voice's native 22.05 kHz, mono). Bearer-token auth
  (`WHISPER_BRIDGE_TOKEN`, the existing shared secret). A text-length cap
  (~6 000 chars — generous for any AIRI answer) is enforced.
- **Resources:** the Piper voice loads once at start; ~150 MB extra RAM
  resident. Synthesis runs faster than real time on CPU — a typical AIRI
  answer (a few sentences) synthesizes in roughly a second. The existing
  `deploy.resources` memory cap is raised modestly to cover it.
- **No persistence, no network egress** — it receives text from llm-proxy2
  and returns audio, nothing else.

## 5. The speak endpoint

`POST /api/airi/speak` (in `app/api/airi.py`):
- Dependencies: `require_admin`, `_require_airi_enabled`, and a new
  `_require_airi_tts_enabled`.
- Body: `{ "text": "..." }`. Empty text → 400; text over the cap → 413.
- Forwards to `settings.airi_whisper_bridge_url` + `/speak` with the bearer
  token; streams the `audio/wav` response straight back to the browser.
- On a bridge failure: a clean JSON error, no stack — the panel silently
  falls back to text-only (a failed read-aloud must never break the chat).
- The text and audio are not persisted; they live only for the request.

## 6. The frontend — the speaker toggle

In `AiriChatPanel`:
- A **speaker button** beside the mic. Renders only when `airi_enabled`
  *and* `airi_tts_enabled` (a new field on `GET /api/airi/status`).
- **Off (default):** AIRI is silent, exactly as today.
- **On:** when an assistant `message` event finishes streaming, its final
  text is POSTed to `/api/airi/speak`; the returned clip is played through a
  single reused `<audio>` element. Only plain assistant text is spoken —
  proposal cards and error bubbles are not read aloud.
- States on the button: **off** → **on/idle** → **synthesizing** (spinner)
  → **speaking** (the button becomes a stop control; tap to halt playback).
- One utterance at a time: a new assistant message stops any in-progress
  playback before it speaks, so AIRI never talks over itself.
- A synth or playback failure is swallowed to a quiet inline note; the
  conversation is unaffected.
- Audio playback needs no special permission (unlike mic capture); it does
  need the toggle to have been turned on by a user gesture, which it is.

## 7. Config & feature flags

- `airi_tts_enabled: bool = False` (`AIRI_TTS_ENABLED`) — the v4.3 feature
  flag, same discipline as `airi_enabled` / `airi_voice_enabled`. Off until
  the build is complete and QA'd. Independent of `airi_voice_enabled` — an
  operator can run input without output, or the reverse.
- `airi_whisper_bridge_url` / `airi_whisper_bridge_token` — reused
  unchanged; `/speak` is just another route on the same sidecar.
- Sidecar env: `PIPER_VOICE` (default `en_US-amy-medium`), alongside the
  existing `WHISPER_MODEL` and `WHISPER_BRIDGE_TOKEN`.

## 8. Scope

**v4.3.0** — Piper in the `whisper-bridge` sidecar, `POST /api/airi/speak`,
the speaker toggle in the AIRI chat panel, feature-flagged. AIRI reads its
completed answers aloud.

**Non-goals (v4.3):**
- *Sentence-by-sentence streaming synthesis* — v4.3.0 synthesizes one clip
  per completed message. Speaking each sentence as it streams (lower
  time-to-first-audio) is a worthwhile later option, not v4.3.0.
- *Speaking proposal cards or errors* — only plain assistant prose.
- *A spoken back-and-forth without the panel* — v4.3 still requires the
  chat panel open; a true voice-loop UI is future work.
- *Persisting audio* — synthesized clips are transient.

## 9. Build milestones

1. **TTS backend** — `whisper-bridge` gains `piper-tts` + the baked-in voice
   model + `POST /speak`; `POST /api/airi/speak` in llm-proxy2; the
   `airi_tts_enabled` flag; `GET /api/airi/status` exposes `tts_enabled`.
2. **Speaker-toggle UI** — the speaker button in `AiriChatPanel`, synth on
   message completion, playback through a reused `<audio>` element,
   synthesizing/speaking/stop states, failure handling.

v4.3.0 = milestones 1 + 2. Each milestone is smoke-tested live (a real AIRI
answer synthesized through the real sidecar and played) before it is called
done — the AIRI 4.0 discipline.

## 10. Resolved decisions (2026-05-18)

1. TTS engine = self-hosted OSS **Piper** — consistent with the v4.2
   self-hosted-Whisper decision and the own-the-dependency-chain rule. The
   Web Speech API `speechSynthesis` is rejected for inconsistent
   cross-platform voices and partial remote-voice use.
2. Piper runs in the **existing `whisper-bridge` sidecar**, not a new
   container and not in-process — one voice sidecar for STT, wake word, and
   TTS.
3. Activation = an **opt-in speaker toggle**, default off. Not always-on
   (intrusive) and not auto-tied to voice input (less predictable).
4. v4.3.0 synthesizes **one clip per completed message** — no
   sentence-streaming synthesis yet.
5. Feature-flagged (`airi_tts_enabled`, default off); text and audio are
   transient and never persisted.

## 11. Deployment

v4.3 changes the `whisper-bridge` image (adds Piper + a voice model) and
`llm-proxy2` (the `/speak` endpoint + flag). The deploy is the usual
llm-proxy2 roll **plus** a `whisper-bridge` image bump on each node.

**Images** — `whisper-bridge` rebuilt and pushed as
`dblagbro/whisper-bridge:4.3.0` (+`:latest`); `llm-proxy2` cut to `4.3.0`
via `tools/cut-release.sh`.

**Compose** — bump the `whisper-bridge` image tag to `4.3.0` on each node
(`/home/dblagbro/docker` and `/opt/C1/instance`); optionally add
`PIPER_VOICE` to the `whisper-bridge` env. No new `llm-proxy2` env is
required — `airi_tts_enabled` stays unset until the post-QA flip.

**Order:** push both images → on each node, recreate `whisper-bridge` then
`--force-recreate --no-deps llm-proxy2` → verify. The feature stays dark
(`airi_tts_enabled` unset) until the post-deploy QA passes; flipping it on
is a separate, later step — the established `airi_enabled` discipline.
