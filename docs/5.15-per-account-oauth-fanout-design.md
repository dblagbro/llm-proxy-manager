# v5.15 — Per-account OAuth fan-out (closes #508)

**Status:** design — awaiting operator sign-off before Phase 1 code starts
**Driver:** ccflare-inspired (per-account session pool with round-robin/least-used dispatch); promoted from architectural backlog to "next ship" after hub-team's 2026-06-30 probe killed the v5.13 in-band-refresh path (`2026-06-30-from-hub-cursor-probe-results-no-public-refresh.md`).
**Why this matters now:** with in-band refresh dead and noVNC the deterministic-but-tedious fallback, the cheapest mitigation is reducing the frequency at which any one account hits Cursor's 60-day re-auth ceiling. If one logical `cursor-oauth` provider holds N accounts, the per-account utilization drops to ~1/N and the practical re-auth cadence stretches commensurately.

---

## Scope

Generalize the `cursor-oauth` provider (and any future OAuth provider type — `codex-oauth`, `claude-oauth`, `cursor-oauth`) from "one Provider row = one access_token + one refresh_token" to "one Provider row = N (access_token, refresh_token) rows in a child table." Dispatch picks one account per request via a configurable strategy. Settings UI lets the operator add/remove accounts to a provider.

**Out of scope for v5.15.0:**
- Cross-cluster account synchronization beyond what the existing `cluster/sync.py` already does for the `providers` table (we'll piggyback on it).
- Multi-tenant access control on accounts (covered by v5.15+ #511 RBAC).
- Per-account billing rollups in the Cursor billing worker (Phase 3 if operator wants it).

## Schema

New table `provider_oauth_accounts`:

```sql
CREATE TABLE provider_oauth_accounts (
    id                  TEXT PRIMARY KEY,                -- secrets.token_hex(8)
    provider_id         TEXT NOT NULL,                   -- FK → providers.id
    label               TEXT NOT NULL,                   -- operator-visible (e.g. "ondevin@c1", "ondevin@personal")
    access_token        TEXT NOT NULL,
    refresh_token       TEXT,                            -- nullable (codex-oauth doesn't have one)
    oauth_expires_at    REAL,                            -- unix timestamp; nullable
    enabled             BOOLEAN NOT NULL DEFAULT 1,
    last_used_at        REAL,                            -- updated on each dispatch pick
    utilization_pct     REAL DEFAULT 0,                  -- written by the existing cursor_billing worker
    -- audit
    created_at          DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME DEFAULT CURRENT_TIMESTAMP,
    captured_via        TEXT,                            -- 'manual_paste' | 'oauth_flow' | 'migration_from_provider'
    -- cluster-sync support
    deleted_at          DATETIME,
    last_user_edit_at   REAL,
    FOREIGN KEY (provider_id) REFERENCES providers(id) ON DELETE CASCADE
);

CREATE INDEX ix_paoa_provider ON provider_oauth_accounts(provider_id, enabled);
CREATE INDEX ix_paoa_last_used ON provider_oauth_accounts(provider_id, enabled, last_used_at);
```

The columns `provider_id`, `access_token`, `refresh_token`, `oauth_expires_at` mirror the existing `providers` columns. The migration copies each existing OAuth provider's single token-pair into one row in this table with `captured_via='migration_from_provider'`, then the legacy columns on `providers` become **read-only fallback** (the dispatch path prefers `provider_oauth_accounts` when at least one row exists).

## Dispatch — account selection

Selection strategy is per-provider, set on the `providers` row via a new column:

```sql
ALTER TABLE providers ADD COLUMN oauth_account_strategy TEXT DEFAULT 'least_utilized';
-- values: 'least_utilized' | 'round_robin' | 'least_recently_used'
```

The selector lives at `app/providers/oauth_account_selector.py`:

```python
async def pick_account(provider_id: str, strategy: str) -> ProviderOAuthAccount | None:
    """Returns the next account to use for this provider, or None if no
    enabled accounts exist. Caller falls back to the legacy Provider.api_key
    when None is returned."""
```

Strategies:
- `least_utilized` (DEFAULT): pick the enabled account with lowest `utilization_pct`. Ties broken by oldest `last_used_at`. Best for Cursor where utilization is the real bottleneck.
- `round_robin`: pick the enabled account with oldest `last_used_at`. Simpler; doesn't need the billing worker to be running.
- `least_recently_used`: same as round_robin (kept as a named alias for clarity).

After pick, the dispatcher writes `last_used_at = now()` in a fire-and-forget UPDATE (no DB session held across the upstream call).

## Auto-skip propagation

Existing v5.8.6 `cursor_oauth_expiry_monitor` auto-skips a Provider when its access_token expires. For v5.15.0:
- The monitor scans `provider_oauth_accounts` instead and disables individual accounts (`enabled = false`) without disabling the parent Provider.
- The Provider is auto-skipped only when ALL its accounts are disabled.
- This requires reworking the monitor's claim path (~30 LOC change).

## Cluster sync

The existing `app/cluster/sync.py` already replicates the `providers` table. v5.15.0 adds `provider_oauth_accounts` to the payload using the same LWW + tombstone pattern as v5.0.18 `cluster_peers`. Inputs needed in `sync.py`:
- `_build_sync_payload` — new section `provider_oauth_accounts_payload`
- `_apply_provider_oauth_accounts` — new applier
- `_section_commit("provider_oauth_accounts")` — per-section commit to preserve the v5.0.5 lock-window fix

## Admin endpoints

New routes on the existing `/api/admin/providers/{provider_id}/...`:
- `GET /oauth-accounts` — list accounts for this provider
- `POST /oauth-accounts` — add an account (body: label, access_token, refresh_token, expires_at)
- `PATCH /oauth-accounts/{account_id}` — toggle enabled / edit label
- `DELETE /oauth-accounts/{account_id}` — soft-delete (writes `deleted_at`)
- `POST /oauth-accounts/{account_id}/probe` — manual liveness probe (calls the same per-provider keepalive check used by v5.8.7)

All edits write `compliance_policy_changes` rows (existing v5.1.2 pattern, scope='per_provider', target_id=provider_id) so the audit trail captures who added/removed which account when.

## Frontend (Phase 2)

Add an "Accounts" expanded-section on the existing Provider card:
- List of account rows: label, enabled toggle, utilization_pct progress bar, last_used_at timestamp, expires_at countdown.
- "Add account" button → opens the existing OAuth-flow modal (cursor-oauth uses `cursor_oauth_flow.start_flow` exactly as today). On success the new account row is inserted; the operator names it.
- "Strategy" dropdown bound to the new `oauth_account_strategy` column on Provider.

## Settings (new in `app/config.py`)

- `OAUTH_ACCOUNT_FANOUT_ENABLED` (bool, default `true`) — kill-switch. When false, dispatch falls back to legacy `Provider.api_key` even if accounts exist. Safe-revert for surprise behavior.

*(Operator decision 2026-06-30: no hard cap on accounts per provider — trust the operator, admin endpoint enforces no upper bound.)*

## Slice — three phases

### Phase 1 (v5.15.0) — Schema + admin endpoints, no dispatch change yet

- Add `provider_oauth_accounts` table + migration that copies existing OAuth provider tokens into it.
- Add `oauth_account_strategy` column on `providers`.
- Add admin endpoints (GET / POST / PATCH / DELETE / probe).
- Add settings.
- Cluster-sync wiring for the new table.
- Tests: model exists; migration copies tokens correctly; admin endpoints CRUD; settings present; LWW conflict resolution under cluster sync.
- **No dispatch change yet.** The legacy `Provider.api_key` continues to drive every request. Phase 1 makes the table real and operator-manageable but doesn't change behavior — derisks the rollout.

### Phase 2 (v5.15.1) — Wire dispatch + frontend UI

- `pick_account()` selector + integration at the cursor-oauth dispatch site in `_messages_dispatch.py`.
- Auto-skip propagation rework (account-level instead of provider-level).
- Frontend Accounts panel + "Add account" UX.
- Tests: dispatch picks from accounts when available; falls back to api_key when none; auto-skip drops individual accounts; provider auto-skipped only when all accounts are off; round-robin vs least-utilized strategies pick the right account.

### Phase 3 (v5.15.2, optional) — Per-account billing

- `cursor_billing_worker` writes `utilization_pct` per-account instead of per-provider.
- Per-account expiry monitor.
- Cluster-rollup view in the dashboard.

## Risks + open questions

**R1. Cursor may rate-limit by client-fingerprint, not by token.** If two of our accounts share the same Source-IP + UA, Cursor may bucket them together and rate-limit anyway. Mitigation: Phase 1 doesn't expose this risk (dispatch unchanged); Phase 2 ships a SOCKS5 hint so each account can take a different egress when the operator wires one up.

**R2. Token rotation timing.** When account A's access_token expires mid-flight on a streaming request, dispatch should NOT fail the entire request — the cursor-bridge already handles 401 from cursor.com by surfacing it back, and our CB engages. With multiple accounts, we may want to dispatch a retry-from-different-account on streaming 401 instead. Out of scope for v5.15.0 → log as v5.15.x backlog.

**R3. Account labels collide with operator memory.** Labels like "personal" vs "C1 account" are subject to operator's naming taste. Recommend defaulting the label to `email@<domain>` derived from the JWT `sub` claim when capturable, with operator override.

**R4. Audit trail volume.** Adding/removing accounts writes a `compliance_policy_changes` row. If operator manages 5+ accounts and toggles them frequently, this could pollute the audit dashboard. Mitigation: `compliance_policy_changes.scope` already differentiates; UI can filter `scope='per_provider' AND target_id=...`.

## Operator decisions (2026-06-30)

1. **Default strategy:** `least_utilized`. Confirmed.
2. **Max accounts per provider:** unlimited. No admin-side cap; operator-trusted.
3. **Frontend cadence:** bundle with Phase 2. v5.15.1 = dispatch + frontend Accounts panel together (one larger ship, tighter operator feedback loop on live behavior).
