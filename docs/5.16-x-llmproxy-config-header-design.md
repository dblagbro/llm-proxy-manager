# v5.16 — Consolidated `x-llmproxy-config` policy header (closes #512)

**Status:** design — filler ship; low priority; useful when a caller-side ergonomics ask forces it.
**Driver:** operator + hub team have both floated the shape informally. Each request today can carry ~6-8 `X-Proxy-*` request headers to override proxy behavior (`X-Proxy-Accept-MCP`, `X-Proxy-Reasoning-Effort`, `X-Proxy-Cache-Mode`, `X-Proxy-Fallback-Chain`, `X-Proxy-Cascade-Mode`, `X-Proxy-Model-Family`, etc.). Discoverability is bad, semantics scatter across handlers, and a config sent in one header doesn't survive round-trips through some client libraries that only preserve certain headers.

## Scope

Add ONE optional request header `x-llmproxy-config` that carries a JSON blob. Every setting currently expressible via an `X-Proxy-*` header is expressible in the blob. Individual `X-Proxy-*` headers still work (back-compat); the blob just aggregates.

**Precedence:** individual `X-Proxy-*` headers win over blob keys (explicit-wins-over-general, standard HTTP header pattern). Documented + tested.

**Not in scope:**
- Signed/verified config blobs (RBAC/scope enforcement is v5.15+ #511's job).
- Alternative wire encodings (protobuf, CBOR). JSON only.
- Bulk config resolution across multiple headers (single `x-llmproxy-config` per request).

## Wire format

```
x-llmproxy-config: {"accept_mcp":["read_xlsx"],"reasoning_effort":"high","cache_mode":"aggressive"}
```

Empty object `{}` is valid and no-op. Malformed JSON → 400 with a clear "invalid x-llmproxy-config header" body (no partial parsing to avoid confusing failures).

Blob-key ↔ individual-header mapping (v5.16.0 target):

| Blob key           | Individual header                | Purpose                          |
|--------------------|----------------------------------|----------------------------------|
| `accept_mcp`       | `X-Proxy-Accept-MCP`             | Opt into a suggested MCP tool    |
| `reasoning_effort` | `X-Proxy-Reasoning-Effort`       | Override thinking budget         |
| `cache_mode`       | `X-Proxy-Cache-Mode`             | Cache directive                  |
| `fallback_chain`   | `X-Proxy-Fallback-Chain`         | Explicit provider chain          |
| `cascade_mode`     | `X-Proxy-Cascade-Mode`           | Cheap-first-then-escalate mode   |
| `model_family`     | `X-Proxy-Model-Family`           | Pin to a specific family         |
| `pii_mask`         | `X-Proxy-PII-Mask`               | PII masking on/off               |
| `vision_strip`    | `X-Proxy-Vision-Strip`           | Drop image parts before dispatch |

Extra unknown keys → silently ignored (with a debug-log line so operators can spot typos). Forward-compat for future keys without version-bumping every caller.

## Implementation slice

1. **`app/middleware/config_header.py`** — parses the header once, stashes the merged config on `request.state.llmproxy_config`. Handles JSON decode errors uniformly.
2. **Wire into every handler that reads `X-Proxy-*`:** the pattern becomes `read_from_state_or_header(request, "accept_mcp", "X-Proxy-Accept-MCP")`. About 8 sites in v5.16.0 target.
3. **Tests:** JSON parse edge cases (empty, malformed, non-object); each individual header still wins over blob key; unknown-keys ignored; blob echoed in a `X-LLMProxy-Config-Applied` response header for debuggability.
4. **Docs:** `docs/api-request-headers.md` gets a new "Consolidated config" section.

## Estimated LOC

- Middleware + tests: ~150 LOC
- Read-site refactor: ~40 LOC (one helper, applied at 8 sites)
- Total: ~200 LOC / 2-4h engineering

## Why this hasn't shipped yet

- Individual headers work fine today; the ergonomics win is real but small.
- Contract change is easy to defer to a filler ship between bigger work.
- Best triggered when a caller team asks for it (DevinGPT is the likely first ask when their config surface grows).

## What ships as v5.16.0

The full slice above. Not phase-split; it's small enough to ship in one shot.
