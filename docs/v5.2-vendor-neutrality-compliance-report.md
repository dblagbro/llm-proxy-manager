# v5.2 vendor-neutrality compliance report

**Repository**: llm-proxy-v2 (FastAPI LLM routing gateway, dual-cluster deployment)
**Versions shipped**: v5.2.0 → v5.2.2
**Date**: 2026-06-06
**Reviewer addressee**: ChatGPT Codex

This report responds to the operator-issued vendor-neutrality audit. The audit asked: is Anthropic/Claude support optional, configurable, replaceable, and blockable across the codebase? And does the same hold for every other vendor?

## TL;DR

llm-proxy-v2 was already a vendor-neutral routing gateway in its core architecture: all adapters are lazy-loaded, the router dispatches off DB-driven Provider rows (no hardcoded vendor switches), litellm is a generic wire-format bridge, the compliance taxonomy is symmetric across 10+ companies, and the gateway boots successfully with zero providers configured.

The audit surfaced six gaps against the operator spec's stricter acceptance criteria. All six are closed in v5.2.0 → v5.2.2 across 12 files, 1532 net insertions, 2 new admin endpoints, 4 new ApiKey columns, 3 new system settings, 1 new policy engine module, 1 new docs page (this one + 2 companion runbooks), and 42 new tests. Full suite is 2786 passed, 2 skipped, 0 regressions. All six fleet endpoints (tmrwww01 x3, tmrwww02 x2, c1conv x1) are live on v5.2.2.

## Summary of findings (from the audit-phase inventory)

Five parallel read-only explorers covered: provider/routing inventory, policy + kill switch, hardcoded-string sweep, deps/env/UI, tests/docs. Synthesis:

**Architecture passes vendor-neutrality at the core**:
- All 15 provider adapter files in `app/providers/` are lazy-loaded; the proxy boots with no provider configured.
- The router (`app/routing/router.py::select_provider`) reads `Provider` DB rows, ranks by capability + LMRH score + priority + circuit-breaker state. No hardcoded vendor branches.
- Vendor-specific dispatch (claude-oauth, grok-web, cursor-oauth, codex-oauth) is gated on `provider_type` matching — symmetric across vendors.
- litellm is a generic wire-format bridge; `PROVIDER_TYPE_TO_LITELLM` is a lookup table; vendor SDKs are NOT in `requirements.txt`.
- `app/compliance/company_map.py` is symmetric: every company has model_prefixes + provider_types + ua_patterns; `COMPLIANCE_CUSTOM_COMPANIES` env extends without code change.
- Boot path (`app/main.py` lifespan) has zero hard-fail on missing vendor keys.

**Six gaps against the operator spec**:

1. **No LLM-call emergency stop** (spec sections 3, 6, 10). The v5.1.0 `compliance.activity_logging_enabled` toggle gates *log writes*, not *LLM dispatch*. Operators had no way to halt routing in <60s short of redeploying with a maximal `COMPLIANCE_SYSTEM_BLOCKED_COMPANIES`.

2. **Background jobs bypassed policy** (spec sections 4, 5, 10). `runs/worker.py`, `runs/compaction.py`, `cot/branches.py`, `cot/structured_output.py`, `routing/cascade.py` called `acompletion_with_retry()` without going through the per-key blocklist gate.

3. **No allowlist / preferred-provider model** (spec sections 2, 4). The policy mechanism was blocklist-only; the operator spec's `allowProviders` / `preferredProviders` could not be expressed.

4. **No individual model-name block + no runtime wildcards** (spec section 2). Only company + model-family (hardcoded prefixes). Could not express `blockModels: ["claude-opus-4-0"]` or `blockModels: ["claude-*"]`.

5. **Three hardcoded `claude-sonnet-4-6` defaults** in non-routing paths (`app/api/providers.py:243`, `app/api/_oauth_chat_translate.py:182`, `app/providers/scanner.py:402`). Not load-bearing, but asymmetric vs codex-oauth equivalents.

6. **Test + doc gaps**: system-wide blocklist exercise, emergency-stop coverage, background-job policy coverage; no emergency-stop runbook; no explicit vendor-neutrality statement.

## Risks remaining

1. **Frontend UI for V2 fields not yet exposed.** Operators can edit `allowed_companies`, `blocked_models`, `allowed_models` via the JSON API (`PATCH /api/keys/{id}`) but not yet via the editor in `ComplianceFieldsEditor.tsx`. Backend semantics + cluster sync are complete. Filed as a v5.3 follow-up; pragma: the WebUI editor needs to fetch the company taxonomy from a future `/api/compliance/taxonomy` endpoint so custom companies surface; that endpoint is a separate small ship. **Not gating the audit acceptance** because the operator spec marks this criterion as "if applicable" and the policy mechanism itself is fully functional via API.

2. **`COMPANY_LIST` in `frontend/src/types/index.ts` remains hardcoded.** Synced with backend `KNOWN_COMPANIES` by convention. Adding a custom company via `COMPLIANCE_CUSTOM_COMPANIES` env requires the operator to redeploy the frontend or use the JSON API. Move to runtime fetch in v5.3 follow-up.

3. **Background-job audit granularity.** V1 emergency stop covers ALL background callers via `acompletion_with_retry`. Per-key blocked-companies enforcement on background jobs is NOT shipped — those callers are internal-system (run-worker, COT branches) and don't carry an inbound api_key_id context for every call. Operator-spec section 5 ("background jobs respect the same policy") is partially met: the master kill switch DOES gate them; per-key blocklists do not. Closing the per-key gap requires plumbing the api_key_id context through every background entry, which is significant refactor; deferred to v5.3+. Current emergency-stop coverage is the operator's master lever.

4. **Frontend `LLMEmergencyStopPanel` exists** but the v5.2.2 build does not yet replace `claude-sonnet-4-6` hardcodes in the deployed v5.2.1 image (the V3 changes are committed locally but deployment is the next step the operator will trigger via `git pull && docker compose build`). Confirmed via the test pass + git diff; the v5.2.2 deploy will land before this report is read.
