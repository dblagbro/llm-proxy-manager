## 1. Scope

A full QA of the v4.1.1 release — every feature shipped in the 4.0 → 4.1.1
arc:

- AIRI v4.0 — conversational router interface (milestones 1–5)
- v4.0.1 — mobile app-shell sidebar drawer

- v4.0.3 — per-user notification preferences

## 2. Method

A throwaway smoke container from the **released `dblagbro/llm-proxy2:4.1.1`
image**, on an isolated copy of the production database (10 providers, real
settings, real activity log). `AIRI_ENABLED=true`, cluster disabled. Every
chat turn ran against a real LLM. UI checks drove real Chromium. The
container and DB copy were destroyed after the run. The production fleet was
not touched — it stays on v4.1.1.

The deterministic logic is additionally covered by the unit suite:
**2112 tests passing**.

## 3. Results

### Group A — AIRI chat, grounding, activity log, capabilities (6/6)
Feature flag · explain-routing · grounded provider list (10/10 real names) ·
supervisor-state faithfulness (3 runs agree) · **activity-log grounding** —
the "any 429s?" question routes through `get_error_summary` · **capability
grounding** — the opus-4.7 question routes through `get_model_capabilities`
+ `explain_routing` and answers "emulated, not failed".

### Group B — rules & rule-sets (4/4)
Default rule-set seeded (4 threshold rules) · save-as · activate · restore-default.

### Group C — propose / apply / revert + safety (6/6)
Plain request → pending proposal · dry-run attached · apply · revert ·
over-large change capped by the active rule-set · **adversarial** "disable
every provider" — 0 auto-applied, 10→10 enabled.

### Group D — scheduled rules + kill switch (3/3 + evaluator live-fire)
AIRI proposes a scheduled rule · approved rule lands in the active set ·
automation kill switch ON/OFF · **evaluator live-fire** — a monitor rule
evaluated and fired against real traffic data with **zero LLM calls**.

### Group E — history + cross-user search (4/4)
Chat opens with a `conversation` event · conversation listed for its owner ·
multi-turn transcript persists · cross-user search finds another operator's thread.

### Group F — per-user notification preferences (4/4)
GET returns a sane default for an unconfigured user · PUT saves email +
categories + min-severity · GET reflects the save · a bad email is rejected (400).

### Group G — capability-fit gate (3/3)
A vision request **skips** a non-vision provider · an oversize request
**skips** a small-context provider · a tools+reasoning request is **no longer
skipped** (co-emulation makes it emulable).

### Group H — tool + CoT co-emulation (1/1)
With a provider forced native-in-neither, a real tools + `task=reasoning`
request returned `X-Emulation-Level: enhanced` and a real `tool_use` — both
capabilities emulated together on one provider.

### Group I — robustness (5/5)
Empty `messages[]` → 400 · stale `conversation_id` → fresh thread ·
unauthenticated → 401 · unknown proposal → 404 · unknown conversation → 404.

### Group J — UI (14/14, real Chromium)
All five AIRI panels render (chat, rule-sets, scheduled rules, change log,
**notification prefs**) · chat streams a reply · history/search drawer opens ·
**sticky chat** — the conversation survives navigating away and back ·
mobile: the sidebar is an off-canvas drawer, hamburger opens it, content uses
the full width · **zero console/page errors**.

## 4. Safety properties re-verified

- Two-stage commit — every mutation is a pending proposal first (Group C).
- Blast-radius cap — adversarial bulk-disable applied nothing (Group C).
- Rule-set caps clamp an over-large change (Group C).
- No recurring LLM mutation — the evaluator fired with zero LLM calls (Group D).
- Capability gate never hard-fails — it reorders toward capable providers,
  with a never-empty floor (Group G).
- Co-emulation composes tools + reasoning instead of dropping either (Group H).

## 5. Caveats

- Co-emulation uses a lightweight reasoning-prefixed tool prompt (one call);
  the full multi-pass CoT pipeline is not composed into the tool path — a
  deliberate bound, noted for a future option.
- The capability gate's context check uses a cheap char-based token estimate
  — adequate for gross-overflow gating, not exact accounting.
