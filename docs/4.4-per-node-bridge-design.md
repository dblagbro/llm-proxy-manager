# v4.4 — Per-node bridge auth (architectural arc)

**Status:** **PATH A REJECTED 2026-05-20** by empirical spike (see §3.1
results below). **Path B is the operative plan going forward.** The
v4.4 backend scaffolding (M-2 / M-3 / M-4 / M-5) was implemented and
shipped as dormant code (no behaviour change without
`node_local_session=true` flag); it stays in place and is reused by
Path B for the single-bridge state-tracking + UI.

**Drafted** 2026-05-20 in operator's absence per the "design first,
no rush" directive (memory: `project_backlog_routing_ai_chat`).
**Empirically resolved** the same day via the live spike.

**Supersedes:** the shared-single-bridge architecture documented in
`architecture.md` §"grok-bridge sidecar" → "Sidecar topology". That
section is the **current** baseline (correct as of v4.3.x).

**Closes (when shipped):** BUG-025 (operationally), BUG-046's latent
exposure (the variable-resolver workaround becomes unnecessary), and
the longstanding "operator must SSH into one specific host to re-auth
Grok" UX pain.

---

## 1. The problem we're solving

The current grok-web architecture is a single shared bridge container
(`llm-proxy2-grok-bridge`) running on tmrwww01 only. All 3 proxy
nodes reach it via the public URL stored in
`providers.extra_config.bridge_url`, cluster-synced across the fleet.

This worked at v3.2.x scale but has accumulated three structural
problems:

1. **Operational fragility.** A single bridge crash takes down
   grok-web fleet-wide (BUG-025 — Xvfb startup race in the image
   killed the bridge 2026-05-19; restart + state-clear both failed;
   grok-web has been disabled fleet-wide for ~17 hours and counting).
2. **No graceful degradation.** Because CB state cluster-syncs (per
   `architecture.md` §"Cluster sync"), one node's failed grok-web
   probe trips the CB on every node. There's no per-node "this
   node's grok works, that one doesn't" state.
3. **Operator UX pain.** Re-authenticating the Grok session requires
   SSH into tmrwww01 + driving a VNC session into the bridge's
   browser. Operators on mobile / on the road can't recover.

The 2026-05-19 deferral was the right call short-term (don't patch
around the symptom), but the underlying architecture needs reshaping.
v4.4 is that reshape.

---

## 2. Keystone constraints

From operator-locked memory + the v4.3-era post-mortems:

- **Design first, no rush** — multi-session arc, design doc before
  code.
- **Open-source only** — no paid-SaaS subscription for the bridge
  layer.
- **No backwards-incompatible breaks** for grok-web callers. The
  Provider config shape, the wire path, the `/v1/messages` request
  shape, the response shape — all stay identical at the caller
  boundary.
- **No new fleet credentials** if avoidable. v4.3.5 demonstrated the
  pattern of reusing `COORDINATOR_HMAC_KEY` for cross-service auth;
  v4.4 should not introduce yet another per-pair secret.
- **Re-auth UX must work from a phone.** Operator scenario: car
  charging on the road, Grok session expired, push notification fires,
  operator taps a link, completes re-auth, done. No SSH, no VNC.

---

## 3. The empirical question that gates the design

**Does grok.com tolerate 2–3 concurrent logged-in browser sessions on
the same account from different datacenter IPs?**

Two possible answers drive two different designs:

- **YES** (account tolerates concurrent sessions): v4.4 can be a
  per-node bridge, each holding its own logged-in session for the same
  shared operator account. Each proxy node calls its own
  docker-internal bridge (`http://llm-proxy2-grok-bridge:8443`) —
  fast path, no cross-internet hairpin, per-node CB.
- **NO** (account is single-session): v4.4 keeps a single bridge but
  hardens it — adds a healthcheck, separates Xvfb startup, provides a
  guided cross-host re-auth flow that doesn't require SSH. Less ideal
  but workable.

**This is the only blocking unknown.** Until the spike answers it,
the design below covers both paths and notes which sections branch.

### 3.1 The empirical spike

Standalone task — ~30 minutes, ~$0 cost:

1. Operator has an existing Grok session in browser A. Note the
   `cf_clearance` / `sso` cookies.
2. From a different network (phone hotspot, or a GCP VM), open Grok
   in browser B with the same account login.
3. Observe: does Grok force a logout in browser A, or accept both
   sessions concurrently?
4. While both are open, exercise both for ~10 min — make a few
   chat-completions calls through each.
5. Result: A still logged in → multi-session tolerated → **Path A**.
   A kicked out → single-session enforced → **Path B**.

Spike runbook + outcome should land in `docs/qa-notes.md` before any
v4.4 milestone code starts.

### 3.2 Live spike outcome — 2026-05-20 ⚠ PATH A REJECTED

Operator executed the spike via the **deployed** M-6 per-node bridges
(stronger evidence than the cookie-only theoretical test §3.1
proposed). All 3 bridges built from `dblagbro/llm-proxy2-grok-bridge:v4.4-rc1`,
each with its own logged-in Chromium attempt against the same
operator Grok account, accessed via per-host nginx routes.

| Node | `/api/status` cookies | `logged_in` | Verdict |
|---|---|---|---|
| tmrwww01 (control, ~hours-old session) | `cf_clearance`, `__cf_bm`, `sso`, `x-userid` all True | **true** | session preserved |
| tmrwww02 (fresh login) | `cf_clearance`, `__cf_bm` True; **`sso`/`x-userid` False** | **false** | Grok silently dropped the auth cookies after login flow |
| c1conv (fresh login attempt) | login form returned **"You have been blocked"** before completion | n/a | Grok's abuse-detection rejected the 3rd IP login attempt |

**Reading**: grok.com enforces **single-account-session semantics**.
A second concurrent IP gets quietly de-authed mid-flow; a third gets
account-flagged for suspicious activity outright. Path A is not
feasible with the current grok.com account-safety model.

**Fallback**: Path B (§5). Single hardened bridge stays on tmrwww01.
The two new bridges on tmrwww02 + c1conv were stopped immediately
(`docker stop`) so their 25-min refresh loops don't keep nudging
grok.com's abuse-detection. Containers + volumes retained for any
future re-attempt; nginx routes left in place (harmless when the
local bridge is stopped — variable-resolver from BUG-046 means the
public URL returns 502 on the affected routes without crashing
nginx).

**The v4.4 backend scaffolding** (M-2 schema, M-3 writer, M-4 routing
filter + CB exemption, M-5 admin API + UI) **stays in place** — it
was specifically designed to be a no-op until `node_local_session=true`
is flipped on the provider's extra_config. M-7 is now **not going to
flip**, so the scaffolding remains dormant. The same code is
re-used by Path B's "track this single bridge's auth state across
the cluster" UX (single row per provider, all nodes show the same
data via cluster sync).

**M-1 image hardening is the durable win**: the `xdpyinfo` Xvfb
readiness probe + the docker healthcheck mechanically prevent
BUG-025 regardless of A vs B. Without the spike, M-1 alone took us
from "grok-bridge crashed and undeployable" to "stable and serving".

## 4. Path A — per-node bridge (preferred if the spike permits)

### 4.1 Topology

```
tmrwww01:                                    tmrwww02:
┌─────────────────────┐                     ┌─────────────────────┐
│   llm-proxy2        │                     │   llm-proxy2        │
│        │            │                     │        │            │
│        ▼            │                     │        ▼            │
│   grok-bridge ─────►│ grok.com session A  │   grok-bridge ─────►│ grok.com session B
│   (own Chromium)    │                     │   (own Chromium)    │
└─────────────────────┘                     └─────────────────────┘

c1conv:
┌─────────────────────┐
│   llm-proxy2        │
│        │            │
│        ▼            │
│   grok-bridge ─────►│ grok.com session C
│   (own Chromium)    │
└─────────────────────┘
```

Each node runs its own grok-bridge container. Each bridge holds an
independent logged-in Chromium session for the same operator account.

Provider config keeps `bridge_url` BUT it now resolves
**per-node**:

- tmrwww01 / tmrwww02: `bridge_url = http://llm-proxy2-grok-bridge:8443`
  (docker-internal, fast path)
- c1conv: same docker-internal URL on its own host

The cluster sync still propagates the provider record across the fleet
BUT the `bridge_url` is a per-node-derived value, not a literal one.

### 4.2 Schema additions

New table `provider_node_auth_state`:

```sql
CREATE TABLE provider_node_auth_state (
  provider_id TEXT NOT NULL,
  node_id     TEXT NOT NULL,        -- 'llm-proxy2-www1' etc.
  auth_state  TEXT NOT NULL,        -- 'ok' | 'expired' | 'needs_reauth' |
                                    --   'never_authed' | 'bridge_down'
  last_ok_at  TIMESTAMP,
  last_check_at TIMESTAMP,
  reauth_url  TEXT,                  -- pre-signed deep link the operator clicks
  PRIMARY KEY (provider_id, node_id)
);
```

This table **IS cluster-synced** (so the operator viewing the proxy
admin UI on any node sees the global state) but the `auth_state` rows
are populated by each node observing **its own** bridge — i.e. the
sync is reporting, not commanding.

### 4.3 Routing changes

`app/routing/router.py` gains a per-node filter on grok-web providers:

```python
# pseudocode
if provider.provider_type == "grok-web":
    state = read_node_auth_state(provider.id, this_node_id)
    if state != "ok":
        # This node can't serve this provider; let the cluster's other
        # nodes pick it up via the existing cross-node dispatch path.
        skip_provider("local grok session not OK")
```

This is the **only** routing change. The proxy's existing
cross-node dispatch (when a node lacks capability for the requested
model, it can forward to a peer) handles the rest.

### 4.4 The CB-cluster-sync change

`app/routing/circuit_breaker.py` adds a per-provider exemption: for
providers tagged `node_local_session=True` (a new boolean on
`extra_config`), the CB state does NOT cluster-sync. Each node's CB
tracks its own bridge's health.

This is a minor architecture change but it fixes one of the BUG-025
core pain points: a single node's failure no longer fleet-wides.

### 4.5 UX: cross-node re-auth flow

Operator opens the admin UI, sees the Providers page. For
`Grok-Web-Devin`, instead of one "Login" button:

```
Grok-Web-Devin     ●●●                         [⚙]
  └─ tmrwww01:   ✅ OK (last seen 2 min ago)
  └─ tmrwww02:   ⚠ Needs re-auth         [Re-auth]
  └─ c1conv:     ✅ OK (last seen 5 min ago)
```

Clicking [Re-auth] opens a modal:

> tmrwww02 needs you to re-authenticate Grok.
> [Open Grok login on tmrwww02] (opens noVNC in a new tab,
>                                 targeted at that specific node's bridge)
> Once you've signed in, this status will turn green within 30 s.

The noVNC URL is per-node:
`https://www.voipguru.org/grok-bridge/vnc/?node=tmrwww02`
`https://www2.voipguru.org/grok-bridge/vnc/?node=tmrwww02`
`https://c1conversations-avaya-01.avaya.c1cx.com/grok-bridge/vnc/?node=c1conv`

The operator picks whichever URL their current network can reach.

For **mobile-friendliness**: each node's bridge container exposes a
QR-code endpoint (`/grok-bridge/reauth-qr?node=tmrwww02`) that opens
the noVNC URL — phone scans QR, completes auth, done.

### 4.6 Image hardening (carry-over from BUG-025 post-mortem)

The current bridge image has an Xvfb startup race (`stderr:
ozone_platform_x11.cc(244)] Missing X server or $DISPLAY` on every
fresh container start). v4.4 ships a hardened image:

- **Healthcheck**: docker-compose `healthcheck` probing
  `:8000/healthz` every 30 s (BUG-025's missing piece).
- **Xvfb order**: `start.sh` explicitly waits for Xvfb's PID to be
  alive AND the `$DISPLAY` socket to be present before exec'ing
  uvicorn.
- **Crash policy**: `restart: unless-stopped` with backoff so a
  bridge that genuinely can't start stops thrashing.

These three changes alone would have prevented the 2026-05-19 deferral.

## 5. Path B — single hardened bridge (if the spike forbids multi-session)

If grok.com doesn't tolerate concurrent logged-in sessions, Path A is
impossible. Path B keeps the single shared bridge but addresses the
three structural problems with less radical change.

### 5.1 What stays

- One bridge container on tmrwww01.
- Public URL is still in `bridge_url` for the cluster.
- CB state still cluster-syncs (no per-node session to differentiate).

### 5.2 What changes

- **Image hardening from §4.6** — exactly the same. This is the
  critical change.
- **Cross-node re-auth UX from §4.5** — exactly the same. Even with a
  single bridge, operators on tmrwww02 or c1conv shouldn't need SSH;
  the proxy admin UI on any node should be able to drive a
  re-auth that the bridge picks up.
- **Bridge state in the DB** instead of the proxy's in-memory cache,
  so the bridge's runtime state survives a container recreate. New
  table `bridge_session_state` (single row).
- **A health-on-degradation UX**: when the bridge is in
  `needs_reauth` state, the admin UI shows a sticky banner across
  all 3 nodes (via cluster sync) so the operator notices regardless
  of which node they're on.

### 5.3 Milestones (Path B)

Same M-1, M-2 (renamed), M-3 (renamed), M-5, M-7 (no-op), M-8 (no-op).
Drop M-4, M-6. ~3 days total.

## 6. Open questions for operator

1. **Schedule the spike (§3.1)** — operator-time, 30 minutes. Path A
   vs Path B literally cannot be picked until this completes. **Most
   important blocker.**
2. **Path A naming**: should the per-node container stay named
   `llm-proxy2-grok-bridge` (and the docker-internal DNS just
   resolves to the local one)? Or rename to
   `llm-proxy2-grok-bridge-local` for clarity? The first is less
   churn; the second is more honest. Slight preference for the
   first.
3. **Backwards-compat for `extra_config.bridge_url`**: when v4.4
   ships, the cluster-synced provider record still has the
   `bridge_url=https://www.voipguru.org/...` value from v3.2.x.
   M-7 migrates it; should the proxy in v4.4 also accept the
   old value as a fallback for one release cycle (safer rollout)
   or hard-cut at deploy (cleaner)?
4. **Notification recipient for `auth_state=needs_reauth`**: should
   v4.4 also auto-fire an AIRI notification (the v4.3.6
   `airi_notify` path with dry_run=False) so the operator gets an
   email + push when a node's session expires? Probably yes; small
   addition.
5. **C1 Anthropic Claude's 0 model_capabilities** (CONFIG-001) is
   adjacent — would v4.4 also benefit from auto-scanning models on
   provider create? That's a separate cleanup but worth bundling.

## 7. What this design explicitly does NOT do

- **Does not change the wire protocol.** Callers send and receive
  exactly the same shapes as v4.3.x.
- **Does not introduce a third-party service.** Per the "open-source
  only" rule.
- **Does not require a new fleet credential.** Reuses existing
  cluster-sync mechanisms.
- **Does not change which operator account is logged into Grok.**
  Same account, just per-node sessions (Path A) or hardened single
  session (Path B).
- **Does not address grok-web rate-limiting.** Grok throttling
  (BUG-035's 429 surprise) is upstream behavior; the bridge
  architecture doesn't change it.

---

## 8. Definition of done

- 3 nodes serve grok-web requests independently (Path A) OR a single
  hardened bridge serves all 3 with graceful operator-driven
  re-auth (Path B).
- BUG-025's failure mode (Xvfb startup race) is mechanically
  prevented by the hardened image.
- Operator can re-auth from a phone, on a different network than
  the failing node, without SSH.
- The cluster-sync semantics are documented in `architecture.md` —
  specifically which surfaces are per-node vs synced, and why each
  is the right choice.
- The 3 cross-node assertions from BUG-037's runbook still hold
  under v4.4 (provider-config sync, route degradation, no error
  spike during a partial-fleet upgrade).
- Activity-log error rate on grok-web returns to baseline (<5/24h
  total, all transient upstream rate-limits, no proxy-side
  classification errors).
